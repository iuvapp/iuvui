# Generative UI: mechanisms and implementation patterns

Research date: 2026-09-23.

This research note describes how current generative UI systems turn model output into interactive interfaces. It is a technical survey, not an iuvui product contract or an implementation plan.

## The core mechanism

Generative UI is not one protocol. In the common constrained form, a model selects or composes UI from an application-provided vocabulary rather than directly drawing pixels. The application still owns the actual components, styling, behavior, data access, and authority to perform actions. A typical flow is:

1. The application defines a component catalog and the data or tools that a generated UI may use.
2. The backend gives the model the catalog description and asks for a constrained output format: tool calls, JSON component declarations, or a UI language.
3. A parser or tool runtime validates the output and turns it into a component tree or a choice of prepared components.
4. A trusted renderer materializes the tree or selected component, usually in the client but sometimes on the server. Streaming systems update it as valid fragments arrive.
5. User input changes local state or sends structured events to a tool or backend. The backend validates and authorizes operations independently of the generated UI.

The distinction between _selection/composition_ and _implementation/execution_ is visible in [OpenUI Lang's component library and renderer](https://www.openui.com/docs/openui-lang/overview), [A2UI's catalog and protocol](https://github.com/a2ui-project/a2ui/blob/main/specification/v0_9/docs/a2ui_protocol.md), and [AI SDK UI's tool-specific component rendering](https://ai-sdk.dev/docs/ai-sdk-ui/generative-user-interfaces). It is an architectural inference from those designs, not a universal protocol requirement.

## Two unrelated projects named OpenUI

| Project                                              | What the model produces                                                                    | Primary purpose                                                                                 |
| ---------------------------------------------------- | ------------------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------- |
| [Thesys OpenUI](https://github.com/thesysdev/openui) | OpenUI Lang, a compact, line-oriented declarative program using registered component names | Runtime composition and streaming of interactive UI from an application-owned component library |
| [W&B OpenUI](https://github.com/wandb/openui)        | Generated HTML that can be iterated on and converted to React, Svelte, or Web Components   | Live UI prototyping and code generation                                                         |

W&B OpenUI prompts a model for Tailwind HTML, streams the response through its backend, previews the parsed HTML and JavaScript in an iframe, and can ask the model to convert the result to another framework. It is a code-generation workflow rather than Thesys OpenUI Lang's catalog, parser, and runtime; their identical names should not imply shared APIs or guarantees. [W&B README](https://github.com/wandb/openui/blob/main/README.md); [generation and conversion code](https://github.com/wandb/openui/blob/main/frontend/src/api/openai.ts); [iframe preview code](https://github.com/wandb/openui/blob/main/frontend/src/components/HtmlAnnotator.tsx); [Thesys overview](https://www.openui.com/docs/openui-lang).

## Thesys OpenUI Lang in detail

The application registers React renderers with Zod prop schemas through `defineComponent` and assembles them with `createLibrary`. The library provides component signatures for the generated system prompt and can specify the root component. Positional arguments are mapped to named props by schema key order. The root-first convention lets the shell appear before referenced children arrive. [Component definitions](https://www.openui.com/docs/openui-lang/defining-components); [system prompts](https://www.openui.com/docs/openui-lang/system-prompts).

The model emits one assignment per line, for example `root = Stack([header, table])`, rather than JSX or arbitrary JavaScript. The current v0.5 language also has `$variable` state declarations, `Query` reads, `Mutation` writes, built-in expressions, and action instructions such as `@Run`. A streaming parser resolves references as later statements arrive, reports schema and parse errors, and feeds a React renderer that maps valid element nodes to the registered components. [v0.5 specification](https://www.openui.com/docs/openui-lang/specification-v05); [renderer](https://www.openui.com/docs/openui-lang/renderer); [parser package](https://github.com/thesysdev/openui/blob/main/packages/lang-core/README.md).

Its important v0.5 separation is between generation and execution. The model generates the layout and wiring; the runtime then evaluates reactive state, runs `Query` on load or when dependencies change, and runs `Mutation` only when an action triggers it. A `toolProvider` supplies callable functions or an MCP client. These interactions can proceed without another model call. The documentation's examples are simplified and explicitly require application handling for authentication, errors, and connection lifecycle. [Architecture](https://www.openui.com/docs/openui-lang/architecture); [queries and mutations](https://www.openui.com/docs/openui-lang/queries-mutations); [renderer API](https://www.openui.com/docs/openui-lang/renderer).

The open-source parser/renderer can be used with an application-owned model path. Thesys also documents an optional managed Gateway that validates and corrects output while it streams; that service should not be confused with the core language or local renderer. [OpenUI introduction](https://www.openui.com/docs/openui-lang); [OpenUI Cloud behavior](https://github.com/thesysdev/openui/blob/main/docs/content/docs/openui-cloud/how-it-works.mdx).

These patterns can be combined. For example, an agent may select a tool whose result contains declarative UI, or use a tool to gather data before generating a UI description. The table compares the _model-to-view contract_, not mutually exclusive products.

Rendering location is another independent choice. OpenUI Lang and A2UI map generated descriptions to client-owned components. AI SDK RSC's `streamUI` instead runs a tool's React component generator on the server and streams React Server Components to the client; its documentation currently marks this API experimental and recommends AI SDK UI for production. MCP Apps render a server-provided HTML resource in a client iframe. [OpenUI renderer](https://www.openui.com/docs/openui-lang/renderer); [A2UI introduction](https://developers.googleblog.com/introducing-a2ui-an-open-project-for-agent-driven-interfaces/); [AI SDK RSC streaming components](https://ai-sdk.dev/docs/ai-sdk-rsc/streaming-react-components); [MCP Apps overview](https://apps.extensions.modelcontextprotocol.io/api/documents/Overview.html).

## What makes the interface safe and predictable

- **The output format is a protocol, not executable authority.** A component catalog and schema limit which elements, props, functions, and actions can be requested. OpenUI reports unknown components and invalid props; A2UI validates messages against the negotiated catalog. A prompt helps the model comply, while parser/runtime checks enforce the actual render contract. [OpenUI component definitions](https://www.openui.com/docs/openui-lang/defining-components); [OpenUI renderer errors](https://www.openui.com/docs/openui-lang/renderer); [A2UI catalog and validation](https://github.com/a2ui-project/a2ui/blob/main/specification/v0_9/docs/a2ui_protocol.md).
- **Rendering ownership stays with the host.** Declarative output is mapped to approved components so the app keeps its design system and behavior. A2UI explicitly sends data rather than executable code; MCP Apps instead isolates a supplied HTML application in an iframe with a bridge and content security policy. [A2UI introduction](https://developers.googleblog.com/introducing-a2ui-an-open-project-for-agent-driven-interfaces/); [MCP Apps overview](https://apps.extensions.modelcontextprotocol.io/api/documents/Overview.html); [OpenAI UI guide](https://developers.openai.com/plugins/build/chatgpt-ui).
- **Progressive UI needs partial-state rules.** OpenUI can parse incomplete statements and resolve later references; A2UI lets component definitions refer to children or data that have not arrived yet. The renderer must decide how to display missing data, invalid fragments, and failures without treating a partial stream as a complete command. [OpenUI renderer](https://www.openui.com/docs/openui-lang/renderer); [A2UI protocol](https://github.com/a2ui-project/a2ui/blob/main/specification/v0_9/docs/a2ui_protocol.md).
- **Tool authorization remains an application responsibility.** A generated `Mutation` or action names an operation, but the backend still has to validate arguments, enforce user permissions, and handle errors. OpenUI's docs explicitly call out production authentication; A2UI distinguishes client events from server-side effects. This is a security conclusion drawn from their execution boundaries. [OpenUI architecture](https://www.openui.com/docs/openui-lang/architecture); [A2UI protocol](https://github.com/a2ui-project/a2ui/blob/main/specification/v0_9/docs/a2ui_protocol.md).
- **A code preview has a different risk profile.** W&B OpenUI sends generated HTML and JavaScript to its preview iframe; its `parseHTML` path is a parser and script extractor, not evidence that arbitrary model output has been sanitized for production use. The iframe configuration itself permits scripts and several other capabilities. Treating this workflow as a safe native-component protocol would be an unsupported inference. [HTML parsing code](https://github.com/wandb/openui/blob/main/frontend/src/lib/html.ts); [iframe preview code](https://github.com/wandb/openui/blob/main/frontend/src/components/HtmlAnnotator.tsx).

## Possible implications for iuvui (inference)

iuvui's existing public React components and Registry could serve as an application-approved component catalog. A separate adapter could publish machine-readable component, prop, slot, and action schemas, then map validated model output back to the same canonical React implementations. That fits the repository's package/source equivalence and React peer-dependency boundaries; it does not require changing the components themselves or placing execution authority in Registry metadata. This is a research inference, not an adopted product decision.
